# 对话布置任务 · 设计与验收

> 目标：用户用自然语言说需求 → 系统出可执行方案 → 用户确认或修改 → 派发给主控执行 → 全程能看见谁在忙。
> 适用范围：MultiAgent 管理台「对话」区（右侧顶部）。

## 零、三条硬边界（2026-11-19 加）
| 边界 | 做法 | 为什么 |
|---|---|---|
| **对话必须知道真实任务** | 每次对话注入「当前任务快照」（最近 8 条：id/状态/轮数/耗时/失败原因） | 之前问「任务什么情况」，答「列表是空的」——当时 hub 里有 #41–#45。它说的是自己的待办，不是 hub 的任务 |
| **对话只读** | `--permission-mode plan` | 之前问「审计进度」，它自己拉起子 agent 干了 512 秒。它该给方案，不是动手 |
| **主控不许自写交付物** | 提示词硬约束 + 运行时 warning | #46 主控一个人 239 秒写完 12KB 文档，没派线、没验收，任务却显示 done |

主控自写产物的判据：`有下级 && 本轮无 dispatch && 有 artifacts` → 记一条 warning
「这些交付没有经过第二方验收」。不判失败（有时只有它能写），但任务详情里能看到。

## 一、交互流程

```
1. 说需求          用户在对话区输入自然语言（"帮我清点武器线资产"）
                     ↓
2. Agent 判断      问问题 / 直接答 / 出方案 三选一
                     ├─ 信息不足 → 反问关键点，不猜着出方案
                     ├─ 纯问答   → 直接回答，不出方案
                     └─ 要动手   → 回答末尾输出 ```ma-plan 块
                     ↓
3. 方案卡           前端把方案块渲染成卡片：目标 / 步骤 / 风险 / 折叠的详细要求
                     ↓
4. 用户决定          ├─ 「派给 A 主控」→ 建任务，切到该任务，任务动态开始走
                     ├─ 「接着说，改一改」→ 光标回输入框，说改哪里
                     └─ 忽略，继续聊 → 卡片留在历史里，不派发
                     ↓
5. 执行             主控 + 五线跑任务；对话区仍可继续追问
                     ↓
6. 回流             任务进展看「任务动态」；对话里问"刚才派的任务怎么样了"直接答
```

### 方案块格式（Agent 侧契约）

```ma-plan
{
  "goal": "一句话目标，≤40 字",
  "detail": "可直接派给主控的详细要求：范围、约束、交付物、验收口径",
  "steps": ["第一步", "第二步"],
  "risks": ["可能踩的坑"]
}
```

规则：一个回答最多一个块，放在最后；改需求时重新输出**完整**方案（不是 diff）；
`detail` 必须能独立执行，不能写"如上所述"。

## 二、状态变化

### 节点格子

| 状态 | 触发 | 视觉 |
|---|---|---|
| 待命 `idle` | 无轮次、无对话 | 常规灰边 |
| **对话中** `running` | 该节点有 CLI 对话进程在跑 | **边框点亮 + 流光条**（与任务运行同款） |
| 任务运行 `running` | 有 `state=running` 的轮次 | 同上 |
| 已完成 `done` | 最近一轮 `done` 且通过 | 绿色状态字 |
| 失败 `failed` | 最近一轮 failed / 被打回 | 红色状态字 + 右上角红点「1」 |
| 等回答 `blocked` | 最近一轮在提问 | 蓝色状态字 + 红点 |

**关键规则**：对话不产生轮次记录，所以「忙」由 `/api/chat/busy` 单独提供，
前端合并进 `CHAT_BUSY` 集合，`nodeState()` 优先读它。4 秒轮询一次，变化时才重绘。

### 对话区

| 事件 | 界面 |
|---|---|
| 发送 | 用户气泡立即出现，输入框清空，按钮变「回答中…」 |
| `start` | 新建一条空白 assistant 气泡，开始接收 |
| `thinking` | 灰色斜体思考文字，追加在同一气泡 |
| `tool` | `⚙ 工具名` 小标签 |
| `text` | 正文逐块追加 |
| `plan` | **整条气泡替换为方案卡**（把流式打出的原始 JSON 抹掉） |
| `usage` | 气泡尾部 `12.3k tok · 31s` |
| `done` | 按钮恢复「发送」，停止按钮隐藏 |
| `error` | 红色气泡，按钮恢复 |

## 三、异常情况

| 情况 | 表现 | 处理 |
|---|---|---|
| 方案块 JSON 写坏 | 不显示卡片，当普通回答 | `parsePlan` 返回 null，剥掉块后只留文字，不报错 |
| Agent 不出方案块 | 只有文字 | 正常聊天，用户可追问"给我个方案" |
| Agent 空转（建 todo、反复调工具） | 一直"回答中" | 已用 `--tools` 去掉 Task*；仍有 5 分钟硬超时，超时 kill 并写一条错误进历史 |
| 派发失败（4xx/5xx） | 卡片按钮恢复可点，弹红色 toast | 不消耗卡片，可重试 |
| 重复点派发 | 第二个被拦 | `dispatching` 标志，toast「已经有一个任务在派发中」 |
| 对话进行中再发一句 | 输入被禁 | 按钮 disabled，提示「上一句还没答完」 |
| 对话进程崩溃 | 红色气泡写着退出码和 stderr 末几行 | `close` 时若没收到 `done`/`error`，补发错误并写历史 |
| 刷新页面 | 历史 + 方案卡都还在 | 历史存 `.data/chat/<node>.jsonl`，含 plan 字段 |
| 换节点 | 对话区切到新节点 | 关旧 SSE、拉新历史、重新订阅 |
| SSE 断线 | 不刷错误提示 | EventSource 自动重连；重连后服务端补发最近 500 条事件 |
| 派发后不管它 | 任务照常跑 | 前端拿到 `X-Task-Id` 就断开流，服务端 `gone` 只停止等待，不取消任务 |

## 四、验收标准

### A. 方案生成

- [x] 说"帮我清点武器线资产，出个执行方案" → 30 秒内出方案卡（实测 31.8s）
- [x] 方案含 goal / steps / risks / detail 四项，detail 能独立执行
- [x] 风险项基于真实资料（实测指出了"27 型 vs 18 库存""65 把含 5 占位"的口径矛盾）
- [ ] 纯问答不出卡片（如"现在做到哪了"）—— 待用户验证
- [ ] 追问改需求 → 重新出**完整**方案而非 diff —— 待用户验证

### B. 派发

- [ ] 点「派给 A 主控」→ 任务真的建出来，任务下拉自动切过去
- [ ] 卡片按钮变「已派发 #47」，不能重复点
- [ ] 任务正文 = goal + 空行 + detail
- [ ] 派发失败时卡片可重试

### C. 高亮

- [x] 对话进行中，该节点格子点亮（`/api/chat/busy` 返回 `["b"]`，实测）
- [ ] 回答结束 4 秒内熄灭
- [ ] 任务运行中，参与节点各自点亮（已有能力，回归验证）
- [ ] 对话与任务同时进行时，格子系统不打架

### D. 异常

- [x] 空转被 5 分钟超时打断并留痕（逻辑已实现）
- [ ] 方案块 JSON 写坏时降级成普通文本，界面不崩
- [ ] 刷新页面后方案卡仍在、仍可派发

## 五、明确的边界（不做的）

1. **对话不能打断正在跑的任务轮次**：`codebuddy -p` 是阻塞进程，要停先点「■ 停止运行」。
2. **对话不产生轮次、不验产物**：适合问、看、定方案；正式交付必须走派活（有回执和证据校验）。
3. **对话有 `D:/YourProject` 写权限**（`-y`）：可以改文件，但目前**没有逐次确认**。大改前应先说清动哪几个文件。
4. **只支持 codebuddy 节点**：其他 provider 没有验证过 session 续接。
5. **同一节点同时只能有一轮对话**，不同节点理论可并发，未做压力验证。

## 六、对话记忆（方案1，2026-11-21）

### 四层记忆的分工

| 层 | 文件 | 谁写 | 记什么 |
|---|---|---|---|
| 项目索引 | `.data/memory/context.md` | 人 | 现在在哪、先读哪几份、硬规格 |
| 教训库 | `.data/memory/lessons.md` | `learn` 命令 | 踩过的坑 |
| 任务流水 | `.data/memory/journal.md` | 任务结束自动 | 任务干了什么（取轮次摘要） |
| **对话记忆** | `.data/memory/talk.md` | 对话每轮自动 | **我们聊过什么、你让我记什么** |

### 写入

每轮对话结束（收到 `result` 且非错误）追加一行：

```
- 11-21 04:52 [a] 问：<60 字> → 答：<100 字> ｜ 记：<MEMO 内容>
```

纯字符串截取，**不调模型**——每轮都记的成本必须为零。

`MEMO:` 机制：用户在说「记住」「以后都这样」时，agent 在回答末尾单独一行写
`MEMO: 一句话`，后端正则提取写进 `记：` 段。正文里保留该行，让人看得见它记了什么。

### 读取

对话开场拼进系统提示：

```
【我们之前聊过的（你自己的记忆，最近 12 条）】
```

排在任务流水**之前**——「你和我」的关系比「项目干过什么」更该优先。

### 与 session 的关系

- session 在：模型有完整上下文，talk 是补充
- **session 断（reset / 换前缀 / 过期）：talk 是唯一把话接上的东西**
- 上限：留 60 条（约两周零散对话），注入最近 12 条、封顶 1000 字

### 验证（2026-11-21 实测）

1. 说「记住：以后所有资产审计必须先出隔离清单给我确认」→ `talk.md` 出现该条，含 `记：` 段
2. **清空 history + session**，只剩 `talk.md`，问「我让你记住的规矩是什么」
3. 8 秒答出：「以后所有资产审计，必须先出隔离清单给你确认，你点头之前不许动任何文件」，
   并自行区分了「对话记忆 / 教训库 / 任务流水」三种来源

### 已知局限

- 摘要会截断（问 60 字、答 100 字），细节靠 session
- `MEMO` 靠模型自觉，可能漏写或写多
- 全局一份、跨节点共享：a 聊的 b 也看得到（省事，但会串味）
- 60 条滚动，更早的会被挤掉——不是完整档案
