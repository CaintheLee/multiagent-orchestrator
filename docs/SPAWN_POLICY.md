# 开线（派生）审批策略

> 三个能力：**参数确认窗口** · **主动开线标准设置** · **审批直接授权给主控**。
> 配置落在 `agents.toml` 的 `[spawn]` 段，与节点配置同源——界面改、手改、备份都是同一个文件。

## 一、后端配置字段

```toml
[spawn]
auto_approve = false        # true：主控自己批，不再等人
defaults_enabled = false    # true：审批时用下面这套值预填
role = "executor"           # 1–32 位字母/数字/下划线/连字符
model = ""                  # 空 = 继承主控
timeout_min = 30            # 1–120
access = "write"            # write | read
task_prefix = ""            # 拼在每个派生任务前面（≤600 字）
```

读取：`loadConfig()` → `Config.spawn`，缺失时用 `DEFAULT_SPAWN`（全关、executor、30 分、write）。
写入：`saveConfig()` 固定写在 `[protocol]` 之后、节点段之前，只写真值部分以外的所有键。

**接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/spawn-settings` | 读当前设置 |
| POST | `/api/spawn-settings` | 保存，返回校验后的值 |
| POST | `/api/approvals/:id` | `{decision, patch?}`；`patch` 只在 approve 时生效 |

## 二、权限判断

| auto_approve | 行为 | 谁能拍板 |
|---|---|---|
| `false`（默认） | 建审批单 → `waitApproval` 阻塞轮询 → 人点批准/拒绝 | **人** |
| `true` | 不建审批单、不等待，直接按当前参数开线并写配置 | **主控** |

两条硬规则：

1. **只有主控能申请派生**（`n.id === cfg.root.id`），非主控一律拒绝，与开关无关。
2. **开关只管「谁按最后一下」**，不管「能不能开」：节点上限 `MAX_NODES`、单任务派生上限
   `MAX_SPAWN_PER_TASK=3`、role/model 合法性校验，两条路上都照跑。

## 三、参数优先级

```
模型显式给的（合法）  >  标准设置（defaults_enabled 时）  >  继承主控
```

逐项：

| 参数 | 来源顺序 |
|---|---|
| role | `spawn.role` → 标准设置 role → `executor` |
| model | `spawn.model`（须过 `SAFE_MODEL`）→ 标准设置 model → 主控 model |
| timeout_min | 标准设置 → 主控的 timeoutMin |
| access | 标准设置 → 主控的 access |
| task | 标准设置 `taskPrefix` + 原任务 |

**关掉 `defaults_enabled` 即完全退回老行为**——标准设置不再参与任何一项，两个开关互不影响。

## 四、状态流转

### 手动模式（auto_approve = false）

```
模型申请 spawn
   → addApproval(状态 pending，payload 已含预填参数)
   → waitApproval 每秒轮询
        ├─ 人点「确认参数并开线」→ 弹窗改参数 → POST approve + patch
        │     → payload 合并 patch → state=approved → 继续开线
        ├─ 人点「拒绝」→ state=rejected → 记 SKIPPED，本轮不派这条活
        ├─ 任务被取消 → state=expired（note: 任务被取消）
        └─ 3 分钟无人处理 → state=expired（note: 没人处理，按拒绝算）
   → 开线成功：写 agents.toml + 加入本次运行树 + 派活
```

### 自动模式（auto_approve = true）

```
模型申请 spawn
   → 不建审批单
   → 直接开线：写 agents.toml + 加入运行树 + 派活
   → 日志「开线已授权给主控，自动批准（套用标准设置）」
```

## 五、前端交互

### 1. 参数确认窗口

审批面板里点「确认参数并开线」→ 弹窗：

| 字段 | 可改 | 校验 |
|---|---|---|
| 节点名 | ❌ 只读 | —— |
| 理由 | ❌ 只读 | —— |
| 角色 | ✅ | `^[A-Za-z0-9_-]{1,32}$` |
| 模型 | ✅ | 留空 = 继承主控 |
| 超时（分） | ✅ | 1–120，整数 |
| 权限 | ✅ 下拉 | read / write |
| 派给它的任务 | ✅ 多行 | 非空才覆盖原值 |

点遮罩或「取消」关闭，不发请求；「确认开线」期间按钮禁用防重复提交。

### 2. 开线设置（主控面板）

折叠区「开线设置」，两个开关 + 四项默认参数 + 派活前缀。摘要行显示当前生效的组合：

```
开线设置· 直接授权 / 标准设置
```

只在首次进面板时读一次（`spawnLoaded`），避免 4 秒轮询把正在编辑的输入框冲掉。保存后立即回显校验结果。

### 3. 待审批提醒

- 工具栏「审核」按钮：平时黑色不发光，有待办时变琥珀色 + 金色脉冲
- 任务动态栏顶部横向提示：`⏸ 等你批准派生「setmap」，批了才会继续派活 · [去批准]`
- 页头金色「待审批 N」

## 六、验收

| # | 场景 | 预期 |
|---|---|---|
| 1 | 两个开关都关 | 每条开线都停下等人，参数由模型给（老行为） |
| 2 | 只开 defaults_enabled | 审批弹窗里预填标准值，人可改 |
| 3 | 只开 auto_approve | 不等审批，直接开；参数仍按模型给的（标准设置不参与） |
| 4 | 两个都开 | 全自动开线，参数按标准设置 |
| 5 | 弹窗里改 role 后批准 | `agents.toml` 与运行时节点都用改后的值 |
| 6 | role 填 `bad role!` | 前端拦下并提示；绕过前端直接打接口也返回 400 |
| 7 | timeout 填 999 | 同上，返回 400 |
| 8 | 关掉 auto_approve | 下一次开线立刻回到等人，不需要重启 |

## 七、已知边界

1. **自动模式下没有任何人工把关**：主控自己批自己开，节点会直接落盘。开之前先确认树不会被灌满。
2. **`task_prefix` 只加在派生任务上**，不影响普通派活。
3. **并发写配置**：两个任务同时开线，后写的会以它读到的快照为准，可能覆盖前一条——概率低，但存在。避免办法是不同时跑多个会开线的任务。
4. **审批单 3 分钟过期**：从 10 分钟改短，因为审批阻塞的是整轮派活（#47 空等五分钟）。

## 八、申请质量要求（2026-11-21 加）

一条新线开出来要跑一整轮、还要落盘占节点。**任务写含糊等于让它自由发挥**，产出的东西没人能验收。

### 提示词里的硬要求

`spawn.task` 必须写清四件事，写在 `prompt.ts` 的 spawn 说明里：

1. **做什么**：范围——读哪些、不改哪些
2. **交付物**：文件名 + 落点路径
3. **验收口径**：怎么算过（数量、字段、抽样要求）
4. **硬约束**：不许动什么、不许覆盖什么

`spawn.why` 要说清「为什么不能塞给现有线」，只写「需要一个新线」不算理由。

### 代码兜底

| 检查 | 阈值 | 处理 |
|---|---|---|
| `task` 去空白后的字数 | < 60 | **直接拒**，不建审批单，报告里写「task 只有 N 字」 |
| `why` 去空白后的字数 | < 12 | 只记提示，**不拒** |

顺序：**role 合法性 → task 长度 → why 提示 → 建审批单**。
role 排最前是因为它是安全校验（挡 `../` 路径穿越），不该被别的检查兜走。
why 不做硬拒：它不是产出质量的关口，拒了只会多一次往返。

### 前端

确认弹窗里，任务框下方显示 `N / 至少 60 字`，不足时数字变红、确认按钮禁用。改了内容实时重算。

### 验收

- [ ] 申请里 task 只有十几个字 → 不弹审批窗，任务报告里出现 SKIPPED 与原因
- [ ] task 够长、why 很短 → 正常弹窗，日志里有一条「why 偏短」的提示
- [ ] 弹窗里把 task 删到 30 字 → 确认按钮变灰

## 九、职责模板（2026-11-21 加）

### 之前的问题

`role` 是自由字符串，模型写什么就是什么。更糟的是 `buildPrompt` 里这段：

```ts
const role = roleFile && fs.existsSync(roleFile) ? 读出模板 : ROLE_FALLBACK;
```

**模板不存在就静默退化成通用兜底**——新开的那条线跑起来没有任何角色约束，
日志、界面、报告里一处提示都没有。这是「职责没有预设模板」的实质。

### 现在

**① 后端列清单** `GET /api/roles`

扫 `prompts/*.md`，解析标题与分组：

```json
{ "id": "a3-audit", "title": "审计（平级 · 只认事实） · PASS/FAIL + 证据，不给建议", "group": "编排" }
```

现有 37 个模板，6 个分组：编排(5) / 工程(7) / 控制台(3) / 文档(3) / 通用附加段(5) / 未分组(14)。

**② 派生时校验**

`roleExists(role)` 为假 → 退回 `executor`，日志写一行：

```
派生 xxx：role「auditor」没有对应模板，退回 executor
```

不再静默退化。

**③ 前端从模板里选**

- 开线确认弹窗的「角色」：`<select>` 按分组 `optgroup`，选项显示 `id · 标题`
- 开线设置里的「角色」：同一份下拉，启动时由 `loadRoles()` 填充
- 清单没加载成功时，退化成只读一项「（模板清单未加载，刷新重试）」，不让人误以为角色被清空

### 已知

- 14 个模板没有 `> 分组：` 行，统一归到「未分组」
- 分组名按第一个 `·` 截断，避免把整句说明撑进下拉标题

### 验收

- [ ] 开线弹窗里角色是下拉，选项按分组排
- [ ] 选 `a3-audit` 开线，任务日志里能看到它按审计角色干活（PASS/FAIL + 证据，不给建议）
- [ ] 手改 `agents.toml` 把 role 写成 `auditor`，下次开线日志出现「没有对应模板，退回 executor」

## 十、角色适用说明（2026-11-21 加）

### 加了什么

`prompts/*.md` 头部新增一行元信息（23 个核心模板已加）：

```markdown
# 审计（平级 · 只认事实） · PASS/FAIL + 证据，不给建议

> 分组：编排
> 适用：独立复核别人的产物、只判过不过、给出证据、不改任何东西
```

`roles.ts` 解析出 `usage` 字段；`GET /api/roles` 一并返回。

### 三个使用点

1. **主控提示词**：带队伍的节点会多一段「可用的职责模板」，列 `id：适用说明`。
   主控开线时照着挑，不再一路默认 `executor`。实测主控提示词 3047 字（含这 23 条）。
2. **开线确认弹窗**：角色下拉下面显示当前选中角色的适用说明（切换即更新）。
3. **开线设置面板**：同样有一行说明。

### 覆盖情况

37 个模板里 23 个写了 `> 适用：`，其余 14 个（`anim2d`、`model3d`、`pixel`、`web` 等）
暂时没写，清单里不出现——它们仍可选，只是主控看不到用途描述。

### 验收

- [ ] 主控提示词末尾有「可用的职责模板」一段，至少 20 条
- [ ] 开线弹窗选不同角色，下面那行说明跟着变
- [ ] 选 `a3-audit` 开线，日志里那轮的行为应该是「只判过不过、不改东西」
