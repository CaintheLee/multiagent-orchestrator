## A1 · P0：产物预览完全失效

**现象**

```
$ ls .sandbox/t14/b/
greet.txt

$ GET /api/artifact?path=<repo>/.sandbox/t14/b/greet.txt
403 不在任何节点的工作区内
```

文件明明存在，接口说不在工作区。

**原因**

第 3 步把 `agents.toml` 的 workspace 从绝对路径改成了短名（`"b"`），运行时拼成 `.sandbox/t<taskId>/b`。

但 `/api/artifact` 的归属校验还是老写法：

```ts
const inScope = cfg.nodes.some((n) => {
  let root = path.resolve(n.workspace);   // resolve("b") = <repo>/b
  ...
});
```

`<repo>/b` 这个目录根本不存在，所以任何产物都判定越界。

**为什么没早发现**

第 6 步验收时我只验证了 `/api/tasks/14` 返回的 runs 里有 artifacts 字段，**没有真的点开预览**。

**修复**

改成按 `.sandbox` 根判断，并把老配置的绝对路径也加进去：

```ts
const roots = [realpathSync(process.cwd()/'.sandbox')];
for (const n of cfg.nodes) if (!workspaceIsIsolated(n)) roots.push(realpathSync(n.workspace));
const inScope = roots.some((root) => { const rel = relative(root, real); return !!rel && !rel.startsWith('..'); });
```

**验证**

```
正常产物 200 你好
越界     403 不在任何节点的工作区内
绕路     403 不在任何节点的工作区内      (../ 绕过)
```

## A2 · P1：崩溃后 runs 表留 running 僵尸

**现象**

```sql
SELECT r.id, r.task_id, r.state FROM runs r JOIN tasks t ON r.task_id=t.id
WHERE r.state='running' AND t.state NOT IN ('running','cancelling')
→ #69 #70 #71
```

三个轮次永远停在 running。对应的任务早就是 interrupted 了。

**原因**

`reconcile()` 只改 `tasks` 表，没管 `runs`。轮次的占位行（`allocRunId` 写的 `state='running'`）没人收场。

**后果**

- 界面上如果按 run 状态筛，会看到永久的"运行中"
- 对账逻辑以后要按 run 做判断时会误判

**修复**

reconcile 里加一条，任务改完后统一收轮次：

```sql
UPDATE runs SET state = 'interrupted'
 WHERE state IN ('running','cancelling')
   AND task_id IN (SELECT id FROM tasks WHERE state NOT IN ('running','cancelling'))
```

**验证**：重启后 3 条变成 interrupted，僵尸清零。

## A3 · P1：取消在轮次边界会被记成 failed

**代码**

```ts
const finalState = !rec ? 'failed' : rec.state === 'done' ? 'done' : ...
```

`rec` 为 null 有两种原因：预算用完，或者 `step()` 开头的取消检查返回 null。前者该记 failed，后者该记 canceled。

**触发条件**

用户在两轮之间点取消（上一轮刚结束、下一轮还没起）。窗口很小但真实存在。

**修复**

```ts
const finalState = !rec ? (ac.signal.aborted ? 'canceled' : 'failed') : ...
```

## A4 · P1：客户端断开后 HTTP handler 挂 30 分钟

**代码**

```ts
const unsub = bus.subscribe(taskId, send);
const state = await waitDone(taskId, 30 * 60_000);
```

浏览器关掉后 `res.write` 抛异常被吞掉，但 `waitDone` 还在轮询，最多挂 30 分钟。

**后果**

每关一次页面就留一个挂住的 handler 和一条 DB 轮询。开开关关几十次，内存和句柄都会涨。

**修复**

`waitDone` 加 `stopped` 回调，`req.on('close')` 置位后立刻返回 null，任务继续在 hub 上跑（不取消）。

**验证**：单次测试不容易量化，但逻辑上 close 事件一定触发。

## A5 · P2：修 A2 时引入的 bug —— reconcile 提前 return

**现象**

第一次修完 A2 重启，僵尸还在。

**原因**

```ts
const rows = db.prepare("... WHERE state IN ('running','cancelling')").all();
if (!rows.length) return;     // ← 这里把轮次清理也跳过了
```

当时任务表里已经没有 running 了，所以直接返回，清理语句根本没执行。

**修复**：去掉提前返回，让轮次清理无条件跑一遍。

**教训**：修完必须重启验证，不能只看代码觉得对。

## 未修（记录在案）

| 项 | 影响 | 为什么不修 |
|---|---|---|
| `log_path` 可能指向不存在的文件 | 点"原文"会 404 | 私账写失败时才会发生；404 本身是正确反馈 |
| `/api/state` 读文件不走 DB | 与 `/api/tasks` 可能不一致 | 界面已经不用它了，留着给老脚本兼容 |
| 任务总超时缺失 | 一个任务最坏 4 轮 × 8 分钟 = 32 分钟 | 属于第 7 步压测，要测出合理值再定 |
| 并发上限写死 3 | 无内存依据 | 同上，压测后定 |
| cancel 与 claim 的微秒级竞态 | 极少数情况取消返回 404 但任务在跑 | claim 到 set 之间只有几行，实际窗口太小 |
