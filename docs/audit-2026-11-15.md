## 一、Major（已修）

### M1 · 记录写失败会中断整条派活链

**位置**：`src/runner.ts` `runOnce()` 末尾

**现象**

```ts
for (const w of warnings) log(...);
saveRun(rec);        // ← 抛异常就到此为止
return rec;
```

`saveRun` 走的是 `writeFileSync` + `renameSync`。磁盘满、权限变、文件被占用时都不抛，但**目录不可写**时会抛 `EACCES`。

一旦抛，`runOnce` 中断 → `runTree` 的递归栈整个炸开 → **父轮次已经跑完的结果一并丢失**。

**后果**：一次写盘失败 = 一整棵子树白跑。

**修复**

```ts
try {
  saveRun(rec);
} catch (e) {
  log(`${pad}  警告  记录没写成：${String(e)}（这一轮结果只在下面的返回值里）`);
}
return rec;
```

**验证**：`node --test tests/protocol.test.ts` 12 项仍全过；跑一轮 `#41` 成功落盘。

**遗留**：返回值保住了，但记录永久缺失。要提高可靠性得加 `fsync`（见 Minor m3）。

### M2 · 产物接口可被软链绕过

**位置**：`src/server.ts` `/api/artifact`

**现象**

```ts
const rel = path.relative(path.resolve(n.workspace), abs);
return !!rel && !rel.startsWith('..') && !path.isAbsolute(rel);
```

`path.resolve` 只做字符串规整，**不跟随软链**。

如果某个工作区里有 `link.html` → `%USERPROFILE%/.ssh/id_rsa`，访问 `/api/artifact?path=.../link.html` 能通过归属检查，实际读到的是 ssh 私钥。

**触发条件**：Agent 自己在工作区里创建了指向外部的软链。不是不可能——它写文件时不会检查目标。

**修复**

```ts
// 先解析软链再做归属判断
let real = abs;
try { real = fs.realpathSync(abs); } catch {}
const inScope = cfg.nodes.some((n) => {
  let root = path.resolve(n.workspace);
  try { root = fs.realpathSync(root); } catch {}
  const rel = path.relative(root, real);
  return !!rel && !rel.startsWith('..') && !path.isAbsolute(rel);
});
```

后续 `statSync` 和 `readFileSync` 都改用 `real`。

**为什么是 Major 不是 Critical**：需要「Agent 主动造软链 + 有人调接口」两个条件同时成立，而且只影响本机。

### M3 · CLI 路径硬编码，换机器要改源码

**位置**：`src/adapters/table.ts`

**现象**

```ts
const CODEX_JS = '%USERPROFILE%/Apps/node-v24.8.0-win-x64/...';
```

写死了用户名和 node 目录。换机器、换 node 版本、用 npm 全局安装，都要改源码。

**修复**

```ts
function locate(envVar: string, candidates: string[], label: string): string {
  const fromEnv = process.env[envVar];
  if (fromEnv) {
    if (!fs.existsSync(fromEnv)) throw new Error(`${envVar} 指向的文件不存在：${fromEnv}`);
    return fromEnv;
  }
  for (const c of candidates) if (fs.existsSync(c)) return c;
  throw new Error(`找不到 ${label} 的可执行文件。试过这些位置：…用环境变量 ${envVar} 指定实际路径即可。`);
}
```

三级策略：**环境变量 → 候选位置 → 可照做的报错**。

**实测三种情况**

```
正常:        .../codebuddy-code/bin/codebuddy
未知 plugin: 不认识的 plugin：claude。可选：codex、codebuddy
变量指错:    MA_CODEBUDDY 指向的文件不存在：C:/nope/missing.js
```

## 二、Minor（记录，未改）

### m1 · `migrateLegacy` 每次读取都执行

`loadRuns()` 开头调 `migrateLegacy()`，它先 `existsSync(LEGACY)` 再返回。老文件已改名为 `.migrated`，所以每次只是一次 `existsSync`，微秒级。

**不修**：成本可忽略，改掉反而多一个状态位要维护。

### m2 · `reportText` 用同步读文件

收口轮要读每个产物前 1200 字，用的是 `readFileSync`。

**不修**：单进程 CLI，一轮一次，阻塞几十毫秒。改成异步会让 `reportText` 从同步函数变异步，污染调用链。

### m3 · 记录写入没有 `fsync`

`writeFileSync` 只写到页缓存，`renameSync` 改名。断电时最后一条记录可能丢。

**不修**：每条多几毫秒，对「丢了重跑一次」这个场景不值。

### m4 · `/api/run` 的并发锁只在进程内有效

`let running = false` 挡住同一进程的并发请求，但开两个服务实例（不同端口）就挡不住。

**不修**：现在是单实例使用。真要多实例，上文件锁或 SQLite。
