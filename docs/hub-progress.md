## 已解决（有实测证据）

### P0-1 工作区共享 → 已修

`agents.toml` 改用短名，运行时拼 `.sandbox/t<taskId>/<节点>`。

**验收**：两个任务先后写同名 `same.txt`

```
任务 #3 → .sandbox/t3/b/same.txt  内容「甲」
任务 #4 → .sandbox/t4/b/same.txt  内容「乙」
```

两个文件都在，内容各自正确，没有覆盖。

### P0-2 轮次编号竞争 → 已修

id 改由 `runs` 表 AUTOINCREMENT 分配。先 INSERT 占位，再写文件。

**验收**：

```
历史 63 条导入后 max=63 → 新任务拿到 run #64、#65、#66
```

`json_path` 留空表示这轮没落盘，启动对账时能一眼找出。

### P0-3 私账同源 → 随 P0-2 一并解决

`runs.log_path` 与公账同一个 id，不再有两套号段。

### P1-1 无法取消 → 已修

`RunOpts` 加 `signal`，abort 时按进程树杀。

**验收**：

```
进程树测试：父 + 孙同时退出，248ms
端到端：第 6 秒取消 → 6.3 秒结束，DB 状态 canceled
残留检查：最近 6 分钟内的 codebuddy CLI 进程数 = 0
```

关键改动：`child.kill('SIGKILL')` 换成 `taskkill /T /F`。前者只杀直接子进程，codebuddy 起的孙进程会活下来继续写工作区。

### P1-3 孤儿进程 → 部分修

主动取消已经不留孤儿。**但 hub 崩溃/被强杀时仍会留**——那需要 Job Object 或启动时按 pid + 创建时间清理，属于第 4 步的对账。

## 第 4 步验收（hub 与调度器）

`server.ts` 现在就是 hub 本身：进程级 DB + 调度器 + 日志总线，一个进程一个 hub。

### 并发上限

```
投 5 个 → #6/#7/#8 running，#9/#10 queued，inflight=[6,7,8]
```

### 取消与补位

```
取消 #6 → 202 cancelling
6 秒后：#6 canceled，#9 从 queued 变 running，inflight=[7,8,9]
```

槽位释放正确，队列自动推进。

### 崩溃对账

强制终止 hub 后重启：

```
#7/#8/#9 running → interrupted（error_code=hub_restart）
#10 queued → running（自动重新加载）
```

**意外收获：崩溃后没有孤儿进程。** 用进程列表精确查过，最近 8 分钟内没有 codebuddy CLI 残留。

原因是子进程继承了 stdio 管道，hub 一死管道断开，子进程写输出失败就退了。这是**运气不是保证**——换成 detached 就会留孤儿。所以审计要求的 Job Object 仍然成立，只是优先级可以降。

### CLI 成为客户端

```
hub 在   → 投递，走排队/并发/恢复
hub 不在 → 本地跑，直接建 running（避免建出来到改状态之间被调度器认领）
--local  → 强制本地
```

实测：走 hub 57 秒，--local 130 秒。

## 现在的行为（可验证）

```
node src/host/cli.ts run --node b --task "..."
  → openDB + 导入历史（幂等）
  → createTask（存配置快照）
  → state: queued → running
  → runTree(ctx={db, taskId, root})
      → 每轮 allocRunId（DB 分配）
      → workspace = .sandbox/t<taskId>/<node>
      → 落盘 runs/<id>.json + logs/<id>.log
      → finishRun（补全 json_path / log_path / phase / verdict）
  → state: done | failed
```

设计约束：`--dry-run` 不建目录、不占号、不落库。
