# 产线并发：把派活从串行改成按车道并行

> 改动时间：2026-11-15
> 触发问题：主控一次派 N 条活，N 条排队跑，五条线要等半小时以上

---

## 一、改之前是什么样

`src/runner/runTree.ts` 里：

```ts
for (const d of rec.dispatch) {
  const kr = await step(kid, d.task, rec.id, false, '');
  if (kr) reports.push(reportText(kr, kid));
}
```

`await` 在循环里，一条跑完才轮到下一条。hub 的 `maxConcurrent: 3` 是**任务级**并发，管不到任务内部的轮次。

实测 #21（五条产线）：`#93 a 206s → #94 d 252s → #95 e 480s(超时) → #96 e 412s → #97 f 480s(超时) → #98 f 376s`，总时长 **38 分钟**。

---

## 二、现在是什么样

```
主控派 3 条
  ├─ lane b ──→ 跑 ──→ 交付
  ├─ lane c ──→ 跑 ──→ 交付
  ├─ lane d ──→ 跑 ──→ 交付
  └─ 全局车位 3：第 4 条起排队，谁空出车位谁上
三条都结束 → 主控收口（每路必有一份交代）
```

### 车道键 = 执行节点 id

不是随便挑的。一个节点只有一个工作区 `.sandbox/t<任务>/<节点>`，两个进程同时往里写就是真冲突。所以：

- **同节点必须串行**——这是约束，不是保守
- **不同节点天然隔离**——可以并行
- 并行度 = `min(派活涉及的节点数, 车位上限)`

派 5 条给 3 个节点，最多 3 路；派 5 条全给 b，就是串行。这不是"用不满"，是正确的。

### 四条不能破的保证（都有单测）

| 保证 | 破了会怎样 |
|---|---|
| 同车道串行 | 两个进程写同一个工作区，产物互相覆盖 |
| 一条失败不断链 | 同车道后续的活永远不会执行，静默丢失 |
| 结果按输入下标归位 | reports 顺序错乱，收口 brief 张冠李戴 |
| 车位一定归还 | 异常路径没 release，直接死锁 |

### 收口契约：每一路都要有交代

抛异常 → 写 `ERROR` 占位；被守门员跳过 → 写 `SKIPPED` 占位并注明原因。
否则 `reports.length` 不足，主控会以为活派丢了。

---

## 三、预算语义改了（这是既有 bug，不是并发引入的）

原来的 `MAX_ROUNDS = 6`，每个 `step` 扣 1，收口轮也扣。主控一次派 5 条：`1 + 5 = 6`，收口轮必然被 `guard` 拦下，**拿不到任何验收结论**。串行也会炸，只是 #19 被打断没跑到收口，一直没暴露。

现在：

- `MAX_ROUNDS = 12`，只作"防派活爆炸"的天花板
- **收口轮完全不占预算、不受 guard 约束**——它是流程必经，被拦住就等于任务永远没有结论
- 新增 `MAX_FANOUT = 8`：一轮派超过 8 条就截断并告警

真正防浪费的还是 guard 的两条：单节点打回 3 次、两次打回同一段话。

## 四、guard 改为按节点判定

`guard` 原来读全树的 `thisRun`，取最后两条打回比较前 80 字。并发下 `thisRun` 的顺序是**完成顺序**，两条不同产线的正常打回会被误判成"同一段话在空转"，整棵树提前停。

现在调用处先过滤：`guard(thisRun.filter(r => r.node === n.id), budget)`。

`tests/guard.test.ts` 里加了一条用例，先证明"混着判会误停"，再证明"按节点判不会"。

## 五、车位申请点是 runOnce，不是 runLanes

`server.ts` 创建**一个** `Semaphore(MA_CONCURRENCY)`，注入 scheduler，再传给每次 `runTree`。

车位在 `runOnce` 里申请（`await pool.acquire()` 包住 `runAgent`），**不在 `runLanes` 里**。原因是主控轮不经过 `runLanes`——它是 `step` 直接调的。如果只在 `runLanes` 申请，主控轮就完全不受约束：3 个任务同时跑就是 3 个主控进程 + 3 个子轮 = 6 个。

两边都申请会死锁：`runLanes` 占满 3 个车位，每个 `runOnce` 再申请 3 个，自己等自己。所以车位只有一个申请点。

顺带处理了取消：`acquire` 返回后先查 `signal.aborted`，已取消就不起进程，直接构造 canceled 结果，避免"白起一个再杀"。

`/api/health` 和 `/api/agents` 都返回 `lanes: { active, waiting, max }`，界面显示成 `N 任务在跑 · 车位 x/3`。注意任务数不受池约束，只有真正起进程的轮次占车位。

## 八、已知边界

1. **外部写盘不防**。codebuddy 没有沙箱（`table.ts` 里只有 codex 会传 `--sandbox read-only`），`checkArtifacts` 只校验回执里**声明的路径**，而且发生在写盘之后。两条线同时用绝对路径写 `D:/YourProject` 仍会撞车。目前靠任务里写死"只写文件名"的约定。
2. **超时没改**。子节点仍是 8 分钟。#21 里 e、f 都是撞 480 秒被杀后重试才成功的。并发解决排队，解决不了"活太大"。要把 8 提到 12，得在界面里逐个改，属于成本决策。
3. **收口时长 = 最慢那条**，不是平均。一条超时 8 分钟，整体就卡 8 分钟。
4. **取消是全停**，不支持单条产线取消。
5. **界面会短暂失真**。`allocRunId` 在抢车位之前，所以排队的轮次在列表里也显示「运行中」。日志会打一行「等车位：3/3 占满，前面 N 条」说明真相。

## 九、第一轮审计发现并修掉的三处

写完当天做的自查，三处都是真问题：

1. **主控轮不占车位**（P0）。车位只在 `runLanes` 里申请，而主控轮绕过它。实测 3 个任务同时跑会有 6 个进程。已把申请点下沉到 `runOnce`，同时删掉 `runLanes` 里的申请（否则自己锁自己）。修后实测：主控轮 `lanes.active=1`，两条子轮 `=2`。
2. **一条短 evidence 毁掉整个回执**（P1）。`parseReceipt` 原先对 `evidence` 每条做 ≥6 字硬校验，执行者随手写一句「ok」就让整轮判 `failed`——产物明明已经写出来了。已改成：太短/太长的条目**丢弃**，长度门槛留给验收层（`evidenceProblem`，只在判 pass 时生效）。
3. **`MAX_FANOUT` 截断的活没有交代**（P2）。原来只打一行日志，收口时主控不知道少派了。已补 `SKIPPED` 占位报告。
