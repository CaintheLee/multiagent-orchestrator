# 点对点留言：让子 agent 直接说话，但不破坏现有语义

> 2026-11-16。原本我判断这层不该做，理由是「谁授权、谁负责死锁、产物归属算谁的」。
> 用户要求做，于是把这三个问题当成设计约束来解决，而不是绕开。

---

## 一、三个问题怎么解

### 谁授权通信

**规则：同一任务内、树上的节点可以互发；跨任务一律不行。**

- 收件人必须在 `cfg.nodes` 里，否则这条不投（日志记一行「树上没有这个节点」）
- 不能发给自己
- 所有留言写进 `messages` 表，带 `from` / `to` / `run_id`，界面「任务动态」里能看到每一条
- 主控可以看到全部（它本来就在收口时读所有报告），子节点只能看到写给自己的

授权不是靠模型自觉，是靠 `task_id` 隔离 + 收件人存在性校验。

### 谁负责死锁

**规则：留言是异步投递，发完就走，不等回话。**

这是整个设计最关键的一条。没有等待就没有死锁——不需要超时、不需要重试、不需要谁当仲裁。

- 发送方在回执的 `tell` 里写一条，写库后立刻继续跑，不阻塞
- 接收方在**下一次开工前**读走，注入提示词
- 对方这一轮已经跑完了？消息留在库里 pending，等它下次被派活时再投
- 一直没人收？任务结束时 `dropPending` 全部作废，不留僵尸

代价是「消息可能永远送不到」。这是可接受的：留言是**附注**，不是任务数据。真要传关键信息，应该走 dispatch。

### 产物归属算谁的

**规则：留言里不能声明产物。**

产物只有一条路：写在自己 workspace 里，在 `artifacts` 里声明，由 `checkArtifacts` 校验路径。

`tell` 的每一项只有 `to` 和 `msg`，schema 里没有任何字段能挂产物。模型就算在正文里写「文件在 D:\x\y.txt」，那也只是文字——收口时 `checkArtifacts` 不会认，主控也读不到（除非那个路径真在某个 workspace 里）。

收口语义因此完全不变：**验收的永远是 artifacts，不是留言**。

## 二、协议

```json
"tell": [
  { "to": "c", "msg": "地图线接缝我定成 4px，你物品摆放时注意对齐" }
]
```

- `to`：节点名，规则与节点 id 一致（1–8 位小写字母/数字/下划线/连字符），自动转小写
- `msg`：必填，≤ 500 字
- 单轮最多 3 条，超了截断（不判整轮失败）

## 三、投递链路

```
b 回执带 tell
  → runTree 校验 to 在树上、不是自己
  → addMessage(task_id, run_id, 'b', 'c', msg)   state=pending
  → 日志：[b] 留言 → c：地图线接缝我定成 4px…

（下一次 c 开工时）
  → takeMessages(task_id, 'c')                  读 + 立刻标 delivered
  → buildPrompt 注入「## 别人给你留的话」
  → 日志：[c] 收到 1 条留言
```

注入位置在**任务正文之前**、项目记忆之后。给模型的话是：

> 同一条任务里的其他线，读完照它调整，不用回复

## 四、为什么不做成请求-响应

那需要：发送方阻塞等待 → 需要超时 → 需要取消传播 → 需要「对方正在跑，消息排队还是抢占」的仲裁 → 死锁检测。四层复杂度，换来的是「b 能问 c 一个问题」。

实际场景里，b 需要问 c 的事，主控在派活时就应该写清楚。真到了要临时问的地步，说明主控的拆解有问题，应该打回的是拆解，不是加一条通信链路。

## 五、验证

任务 #31：主控派 b 写 `m_b.txt`，并要求 b 在回执里给 a 留言。

实际结果：

```
#136 a 主控   49s  派 b 一条
#137 b 执行  250s  写出 m_b.txt，回执带 tell
      → messages 表：b → a  delivered
#138 a 收口   16s  PASS（开工前取走了那条留言）
```

数据库里能查到 `b → a · delivered · b 线已交付 m_b.txt，三行齐全，无需返工`。
收口轮只用 16 秒就判过——它不用再猜「b 到底交没交」，留言里写着。

前面两次失败（#29、#30）分别是「留言块位置错」和「对象当数组被拒」，都记在第七节。

## 六、已知边界

1. **消息不重投**。这一轮失败重试，消息已经标记 delivered，不会二次注入。重复投递比丢一条更糟。
2. **只投一次给一个人**。没有广播，没有抄送。
3. **任务结束即作废**。跨任务的「长期信箱」是另一个设计，现在不做。
4. **消息不进收口简报**。主控收口时看到的是 reports，不是 messages。留言影响的是「下一轮怎么干」，不是「这一轮算不算过」。

## 七、实现中踩的三个坑（都是真踩到的）

**1. 留言处理放错了位置。** 最初写在「这一轮有 dispatch 才继续」的分支之后。可执行者（b）没有 dispatch，会在那之前 `return rec`——它写下的留言一条都发不出去，而日志里什么异常都没有。第一次验证就是这样：b 的 `tell` 明明记录在案，`messages` 表却是空的。

修法：挪到 `runOne` 之后、任何 `return` 之前。留言不依赖派活。

**2. `tell` 写错格式会毁掉整轮。** b 把 `tell` 写成了对象而不是数组：

```json
"tell": {"to":"a","msg":"b 线已交付 m_b.txt"}
```

`parseReceipt` 判「tell 必须是数组」→ 整轮回执作废 → 文件写好了却算 failed。这和之前 evidence 太短毁整轮是同一个反模式。

修法：**单个对象自动包成数组，坏条目直接丢弃**。理由：留言是附注，一句话没写好不该让整份交付作废。

**3. 收口简报里没有留言。** 主控看不到 b 给谁留了什么话，只能从 summary 猜，结果误判「tell 格式错误，要求重写」。

修法：`reportText` 加一行 `- 它给 a 留了话：…`。主控据此判断「话送到了没有」，而不是靠猜。

第 2、3 条的共同教训：**新字段要么全程宽松，要么全程可见**。只做一半，就会变成「模型写对才能过，写错就白跑一轮」。
